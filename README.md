# 2D Stock Cutting

A locally hosted web application for planning how to cut rectangular items from sheets already in stock. You load the
items and the sheets, choose how stock should be valued, and the application returns a cutting plan, what to buy in,
and a drawing of every pattern with each item placed exactly, against the clearance rules.

The web page talks to a Julia backend on your own machine. Nothing leaves it: the server listens on the loopback
address only.

## Starting it

You need [Julia](https://julialang.org/downloads/) 1.10 or later (tested on 1.12) with `julia` on the path, and a
current browser. It runs on macOS and Windows (and Linux).

| System | Start |
| --- | --- |
| macOS | double-click `start.command`, or run `./start.sh` |
| Windows | double-click `start.bat` |
| Any | `julia --project app/server.jl --open` |

The scripts check that Julia is installed, install the packages, start the server and open the page. The first start
installs the packages, which needs an internet connection and takes a few minutes. Later starts take a few seconds.
If the port is already in use (another copy is running), the server says so and stops. On macOS, if the scripts will not
open after being copied or unzipped, run `chmod +x start.sh start.command` once in a terminal. The page is at <http://127.0.0.1:8765>. Press Ctrl+C in the terminal to stop it. The address and the port
are `APP_HOST` and `APP_PORT` in `solver/src/constants.jl`.

Each run starts its own Julia process, so a run takes about ten seconds to start before it begins solving.

## Using it

1. **Data.** Upload the items and sheets as CSV files, or type them into the tables (cells can also be pasted from a
   spreadsheet). The page checks the data as you go, marks any bad cells, and lists the groups it found. Tick the groups
   to run.
2. **Settings.** Choose what to run, the clearance, and how the sheets are valued.
3. **Run.** Start the run and follow it. It can be cancelled, and finished groups are kept. Earlier runs are listed,
   and a run's data and settings can be loaded back into the page.
4. **Results.** For each group: how many items are demanded, made from the sheets, bought in (with their value) and
   left over, how many sheets are used and left over, the waste on the sheets used, what happens to each item and each
   sheet size, and a drawing of every pattern. Click a drawing to enlarge it and to see the position of every item. The
   results can be downloaded as JSON, which also holds the solver's details, and the cutting plan (every item of every
   pattern, with its position) as CSV.

### The data

All sizes are in millimetres. Headings are matched ignoring capital letters, and the columns can be in any order.
Downloadable templates are in `web/templates/`.

**Items**

| Column | Needed | Meaning |
| --- | --- | --- |
| `item_id` | yes | A name for the item. Each must be different. |
| `value` | yes | What one item is worth. This is what it costs to buy one in. |
| `width`, `height` | yes | Size of the item. |
| `thickness`, `material`, `finish` | no | Items are only cut from sheets with the same three. |
| `can_rotate` | yes | `yes` if the item may be turned through 90 degrees, otherwise `no`. |
| `demand_period_1`, `demand_period_2`, ... | yes | The number needed in each period. |

With only `demand_period_1` filled in, that is the demand for a year, planned as one period. With more periods, the
plan is made period by period, and the settings ask how many periods make up a year.

**Sheets**

| Column | Needed | Meaning |
| --- | --- | --- |
| `sheet_id` | yes | A name for the sheet size. Each must be different. |
| `width`, `height` | yes | Size of the sheet. |
| `thickness`, `material`, `finish` | no | As for items. |
| `quantity` | yes | How many sheets of this size are in stock. |

**Rotation.** An item that cannot be rotated is placed with its width along the width of the sheet and its height along
the height of the sheet. This assumes the width and height of each sheet are given in the same orientation as the items
(for example, the same grain direction).

**Groups.** Each combination of thickness, material and finish is solved on its own, with only the items and sheets that
match it. An empty cell is its own value, so items with no material match sheets with no material.

### The settings

- **Cutting plan from the sheets in stock.** Chooses which patterns to cut from the sheets and how many times, and what
  to buy in. Patterns are generated by column generation, with the three-staged dynamic programme (all six speed-ups)
  pricing the patterns. The integer programme then chooses the plan from the patterns found.
  - *Seed the pattern pool with dichotomic patterns* first generates a wide set of patterns by the dichotomic search and
    starts column generation from them. It takes extra time and may give a marginally better plan.
  - *Months of cover* also works out how many whole months of each item's demand the stock covers when it is used for
    profit alone (the runways), with the patterns of the column generation run.
- **Infinite sheet.** The length of roll that would meet a year's demand if material were unlimited. The roll is cut
  into shelves, each a row across the full width of the roll, laid end to end. Its clearance is its own: a gap and
  separate left, right, top and bottom margins, with a button that copies the values of the sheet stock's clearance
  across. A shelf is as wide as the roll less the left and right margins, and at most as tall as the tallest shelf you
  give less the top and bottom margins. Along the roll, shelves are separated by the gap, with one more gap at each end,
  so the top and bottom margins only limit how tall a shelf can be. The gap and all four margins must all be 0, or all
  be above 0. Give the roll width for each group. Items too wide or too tall for the roll are left out and listed.
  Each shelf is drawn as a sheet as wide as the roll and as tall as the shelf plus the gap above and below, with the
  left and right margins at its sides, and the results have a "View the roll" button that opens a window to scroll along the roll with the shelves stacked, by kind,
  tallest first (the plan gives how many of each shelf to cut, not their order).
- **Clearance.** The gap between neighbouring items, and the margin at each edge of the sheet. A margin of 0 lets items
  sit flush with that edge; above 0 it is a minimum distance.
- **How the plan is chosen.** Buying in is the last resort, and there is nothing to set.
  - With too few sheets to meet the demand, every sheet that can supply an item still short is cut, and what the
    sheets cannot supply is bought in.
  - With more sheets than the demand needs, nothing is bought in, and the sheets cut are the ones that give up the
    least. Each sheet is valued at its best packing (the most valuable pattern that fits on it), whatever the demand
    for the items on it, so the least valuable sheets are used and the most valuable are saved.
  - A sheet that can hold none of the items is never cut.
  - The demand is the demand in the data, summed over all its periods.
- **Holding cost of items** (a share of value a year). Items in stock at the end of a period are charged that yearly
  rate divided by the number of periods in a year, and so are items left at the end of the last period, which is one
  extra period. Sheets have no holding cost.
- **Limits.** The most column generation iterations, an optional column generation time limit, and the time the integer
  programme may take on one group. When the integer programme runs out of time, the best plan found so far is kept and
  the result says so.

### The results

Everything shown is computed by the backend: the page only draws it. For each pattern the backend works out the exact
position of every item (`app/layout.jl`) and checks it against the clearance rules: every gap, every edge margin, and
that the items placed are the items the pattern records. A pattern that fails the check is marked, which should never
happen.

A run is stored in `jobs/<id>/`: `input.json` (the data and settings), `result.json`, `status.json`, `log.txt` and
`meta.json`. Positions in `result.json` are in millimetres from the bottom-left corner of the sheet, with y up.

## What is in the folder

```
app/
  server.jl          the web server and its JSON interface
  job_runner.jl      runs one job in its own process: instances, models, placement, results
  data_input.jl      reads and checks the tables, and splits them into groups
  settings.jl        the settings, their defaults, and their checks
  layout.jl          places the items of a pattern and checks the placement
  load_models.jl     loads the models in dependency order
solver/              the models (below)
web/                 the page (index.html, app.js, style.css) and the CSV templates
test/run_tests.jl    tests on small toy instances
jobs/                one folder per run (created when the first run starts)
```

### The models (`solver/`)

| File | What it is |
| --- | --- |
| `src/Pattern_Generation/revised_three-staged_dp.jl` | The three-staged guillotine dynamic programme with six speed-ups, clearance and rotation. |
| `src/Pattern_Generation/fullpack_heuristic.jl` | Rows of single copies, used to start the infinite sheet model. |
| `src/Pattern_Diversification/dichotomic.jl` | Optimal, big-M and dichotomic search patterns for pool seeding. |
| `src/Pattern_Selection/multi_period_ip.jl` | The selection integer programme. One period with one period per year is a single year's demand. |
| `src/Pattern_Selection/multi_period_col_gen.jl` | Column generation over that integer programme. |
| `src/Pattern_Selection/min_month_ip.jl` | The months-of-cover model. |
| `src/Pattern_Selection/infinite_sheet_col_gen.jl` | Column generation for the length of an infinite roll. |
| `helper/` | Shared pieces: data types, clearance grid, pattern pool, sheet costs and the weight on buying in, waste, reporting. |
| `src/constants.jl` | Every constant, including the application's defaults. |

These are copies of the research code. They differ from it in three ways: the single-period model is removed, since the
multi-period model takes one period; the sheet terms of the selection integer programme are replaced by the single
formulation described above (buying in weighted so that it is the last resort, and each sheet cut costing the value of
its best packing), with no valuation setting and no sheet holding cost; and the experiment-only code and constants are
removed.

## Tests

```
julia --project test/run_tests.jl
```

They cover the reading of the tables, the settings, the placement of items under many clearance rules (every layout is
checked), the two cases of the selection model (too few sheets, and plenty) and the holding cost on instances small enough
to work out by hand, and a whole run of the job runner.

## Limits to know about

- One run at a time. A second run is refused until the first finishes or is cancelled.
- Cuts are guillotine cuts. Column generation, the integer programme and the dynamic programme all take longer as the
  sheets get larger relative to the items, so set the time limits to suit.
- Sizes are used as given. Sizes with many decimal places make the dynamic programme slower, because it works on a
  whole-number grid fine enough to hold every size and clearance exactly.
- An item that fits no sheet in its group is bought in, and is marked in the results.
- The solver is HiGHS, which is installed with the packages.
